# E5 — Monitoring et incident

## Preuve de tranche verticale et incident — 24 aout

Les services ecrivent des journaux JSONL structurés ; les champs sensibles,
dont l'adresse IP, y sont pseudonymises. L'identifiant de correlation est
transmis de l'application a l'API, ce qui rend une requete retrouvable de bout
en bout.

Un incident CI reel a ensuite ete reproduit et resolu. La premiere execution
GitHub echouait parce que la table PostgreSQL etait consultee avant son import ;
apres le correctif, la seconde a revele que le paquet installe par UV excluait
les modules `api` et `app`. Les deux causes, les logs, les commits correctifs
et l'execution GitHub de non-regression sont conserves dans
[`docs/incident.md`](../../docs/incident.md). La derniere CI passe la chaine
complete (Spark, PostgreSQL, entrainement, 13 tests et lint) : c'est une preuve
C21 reproductible et non un incident reconstitue apres coup.

Le monitorage applicatif est restitue dans la page locale `/exploitation` :
latences p50/p95, taux d'erreur, seuils, alertes et routes sont lisibles sans
service externe. Les logs JSONL pseudonymises et le `X-Request-ID` permettent
de joindre une action navigateur au POST modele correspondant. Les seuils,
decisions de reponse et la boucle de retour MLOps sont documentes dans
[`docs/monitoring-app.md`](../../docs/monitoring-app.md). La preuve Docker
confirme ce lien de correlation dans un conteneur de preproduction.
