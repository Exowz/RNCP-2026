# E3 — Mise en service du modèle et MLOps (C9–C13)

## 1. Contexte, acteurs, objectifs et contraintes

L'équipe Data Science fictive livre à l'équipe applicative un artefact PyTorch gelé : le moteur qualifie un rapprochement, il ne prédit ni prix ni valeur. L'objectif est de prouver qu'un modèle peut être exposé, testé, monitoré et livré de façon reproductible hors ligne.

## 2. Spécifications fonctionnelles et techniques

L'API modèle doit accepter un rapprochement validé, exiger une clé API, retourner les trois axes indépendants cohérence/anomalie/confiance, expliciter les réserves et publier OpenAPI. Le modèle est chargé depuis `models/concorde_moteur.pt` sans téléchargement ni recalcul de production.

**Décision.** Les trois sorties ne sont jamais fusionnées en une note opaque. Une forte anomalie ne compense pas une contradiction, et une confiance faible ne devient pas un verdict positif. Cette séparation est défendable par les règles et la fiche de modèle.

## 3. Réalisation IA, API et MLOps

`api/model/` expose `/predict`, `/predict/lot`, `/sante`, `/modele/fiche`, `/regles` et `/metriques`. Les schémas Pydantic refusent les entrées inconnues ; les rôles `reader` et `analyst` protègent routes métier et lots. L'application appelle réellement l'API par HTTP, avec le même `X-Request-ID` dans les deux logs.

L'entraînement sépare train/validation/test par mutation, calcule les références sur train seul, calibre l'autoencodeur, publie métriques et fiche, puis journalise dans MLflow SQLite local. Evidently produit un rapport HTML/JSON de dérive local via `scripts/monitor_model.py`.

## 4. Tests, CI/CD et monitorage

```bash
source scripts/spark-env.sh
uv run python -m concorde.model.entrainement
uv run pytest tests/model tests/api/test_api_modele.py -m "not local_service" -q
uv run python scripts/monitor_model.py
```

Le test C12 entraîne, évalue, écrit un artefact temporaire et le recharge. La CI [32857959387](https://github.com/Exowz/RNCP-2026/actions/runs/32857959387) est verte : fixtures, collecte, entraînement, 53 tests (86 % de couverture), lint, build Python et upload d'un artefact comprenant roue, archive source, modèle, fiche et métriques.

## 5. Bilan, limites et perspectives

Le modèle est servi, explicable et monitoré ; la chaîne C9–C13 est exécutée, non seulement écrite. La limite méthodologique majeure est assumée : les anomalies du jeu de démonstration et certaines règles appartiennent aux mêmes familles, donc les métriques de règles sont circulaires et ne sont pas présentées comme une performance générale. Le rapport de dérive déclenche une revue humaine, jamais un réentraînement automatique.
